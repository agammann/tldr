# Browser bridge security

The local bridge v2 protects captures and shared-session responses from an unrelated process that owns the configured loopback port. The MCP service and unpacked extension must both be 1.0.1 or later; no plaintext fallback is allowed. Pairing remains a random 256-bit key stored locally with the existing file format.

The shared transport module uses HKDF-SHA256 with the protocol name as salt and separate request/response context strings to derive two AES-256-GCM keys. Requests and responses use independently random 96-bit IVs and authenticated data containing the protocol, direction and server challenge. Each server challenge has 256 random bits, expires after ten seconds and is consumed once, including on failed authentication. At most 256 unexpired challenges are retained. A response also binds its encrypted result to the exact request IV and operation.

The token never travels in HTTP headers or request bodies. A fake challenge or a listener substituted between challenge and request receives only ciphertext and cannot forge an accepted reply. A transparent relay can deliver an already-authorized encrypted request, but cannot read or modify its capture or response, and cannot replay it after the challenge is consumed. Host, loopback binding, browser Origin, capture schema, time, size and connection limits still apply. Plaintext payloads are bounded at 1.2 MB; captures reserve 1,024 bytes within that bound for the stored timestamp and authenticated response wrapper. Encoded envelopes are limited to 1.7 MB and challenge replies to 1 KB on clients. Over-limit captures are rejected before replacing the previous snapshot.

The tests exercise a real prebound unrelated listener, listener substitution after a genuine challenge, replay, reflection, modified ciphertext, wrong keys and legitimate multiple MCP sessions. Browser acceptance checks load the actual extension and verify capture through the paired MCP.

This does not protect a compromised browser, assistant, operating-system account or other process that can read the pairing file. Local process interference can still deny service. The source fix does not disprove historical exposure from older versions. See [upgrade and rotation](docs/INSTALL.md#security-update-and-pairing-rotation) before using an earlier pairing when an unknown listener may have been present. No real user's pairing file is changed automatically.
